# Web authoring and databases

Welcome to dewstack. This course is for adults learning to build websites
and work with data. The first tutorials introduce the tools, so you can
begin without knowing how to code.

The [course website](https://deweydex.github.io/dewstack/) has two paths
and a list of tutorials. This README describes the course and links to
current and older materials. Teachers can also find notes about how the
site is made below.

The tutorials and exercises are not graded. Only the two projects and
the exam are, and your teacher covers those in class. That leaves room
to break things and fix them while you are still learning. Something not
working is the normal shape of building a website, not a sign you have
done anything wrong.

[Using dewstack](docs/FOR_STUDENTS.md) explains the page controls and
how to keep your work. The [FAQ](https://deweydex.github.io/dewstack/tutorials/reference/faq/)
answers questions about getting started and learning here.

## Before you begin

You can read the tutorials and try the data exercises in a browser,
without an account or anything to install.

The website exercises use a free GitHub account. GitHub keeps your files
and publishes your website. It also has an editor on its website, so you
can work in your browser. If you prefer an editor on your computer,
VS Code is one option.

[How the pieces fit](https://deweydex.github.io/dewstack/tutorials/getting-started/how-the-pieces-fit/)
introduces these tools. The pages after it explain how to create an
account, prepare your files, and publish a website.

## Two ways to begin

You can begin with a website or with data. If you are learning in class,
your teacher can help you find where to begin. If you are working on
your own, you can choose either path.

### Start with a website

We learn HTML for a page's structure and CSS for its appearance. Along
the way, you build a personal website with an address you can share.

Your website uses your own copy of the **portfolio_wad** repository.
A *repository* holds a project's files and records changes to them.
GitHub calls your own copy a *fork*. After making a copy, you can change
one file at a time and look at the result.

The starter has twenty-five exercises and instructions in its README:
<https://github.com/deweydex/portfolio_wad>

If a change gives an unexpected result, that is a normal part of the
exercise. You can compare it with the example, undo the change, or ask
your teacher to look with you.

### Start with data

A database stores information, such as products in a shop or members of
a club. We begin with information in tables. Then we use SQL, a language
for working with data, to ask questions about it.

[A table is a list of rows](https://deweydex.github.io/dewstack/tutorials/data/a-table-is-a-list-of-rows/)
has the first example. The database runs in your browser. Nothing is
installed, and nothing you type is sent anywhere.

The first four pages introduce tables, questions about their data, and
ways to use two tables together. A box labelled **Your table** keeps
SQL text you run in this browser. The saving section below explains how
this works and how to keep a separate copy.

## Full stack: putting the two together

In this part of the course, we connect a web page to a database. For
example, a visitor might search a list of products or use a form to add
a new product. We bring together the website and data skills from the
earlier tutorials.

The first tutorial is live:
<https://deweydex.github.io/dewstack/tutorials/full-stack/a-page-that-reads-from-a-database/>.
It shows a page whose own JavaScript asks a database a question and
draws what comes back, then adds a search box a visitor can actually
type into. The rest of this part of the course is still being written
and will appear here as it is ready.

The college sets the assessments: a web authoring project, a database

The web authoring project builds on your site from the starter. Lessons

## Where your work is saved

Your website files stay in your GitHub repository when you save them
there. They are yours, not the college's. You can return to them from
any computer by signing in to GitHub. Saving files only on your computer
does not send them to GitHub.

On the data pages, **Your table** saves its SQL text in this browser
when you use **Run** or **Load**. Typing alone does not save it. Pages
with the same **Your table** box load and run that saved text again.
Clearing browser data or using **Reset** removes the saved text. Browser
settings or full storage can also prevent saving.

**Download** keeps the SQL text as a `.sql` file. **Load** puts a file's
text into the box, and **Run** runs it. This lets you keep a separate
copy or move your work to another computer.

Other SQL boxes do not save changes between visits. Their **Download**
button lets you keep the text. In the older playground, copy your SQL
into a file of your own. The small website editors inside tutorials also
start again when you return; **Download these files** keeps a copy.

The [dewstack workspace](https://deweydex.github.io/dewstack/workspace/)
is a page with the same website editor and no tutorial attached. It
keeps several named sites in this browser, on this device, the way
**Your table** keeps its SQL. Use it to try an idea, or press **Open in
the workspace** under a tutorial's editor to keep changing that example.
Your own site still lives in your fork, and **Download these files**
moves a site from the workspace to there.

[Using dewstack](docs/FOR_STUDENTS.md) explains these controls in more
detail.

## For teachers

**How a student's report reaches you.** Most pages carry a line at the
foot, "Something wrong on this page? Tell us.", and a SQL or Python cell
has its own smaller version of the same thing among its own buttons. Both
open the same three doors: a question goes to GitHub Discussions, an
error or a page that is wrong or hard to follow both open a prefilled
GitHub issue — a report opened from a cell's own icon already carries
that cell's id, its current code, and whatever it last showed.
[`docs/REPORTING_A_PROBLEM.md`](docs/REPORTING_A_PROBLEM.md) is the
student-facing version of this; [`.claude/skills/triage-report/SKILL.md`](.claude/skills/triage-report/SKILL.md)
is the order to work an issue in once it arrives, kept as a written skill
rather than something to reinvent each time. `planning/feedback.yaml` is
the switch: `enabled: false` turns the doors off everywhere, without
touching a tutorial, if reports need to pause for any reason. Two more
workflows run against a report once it exists: `label-report` applies a
`page:`/`kind:` label the moment one opens, creating either the first
time it is needed; `report-patterns` runs weekly and opens or updates a
`pattern` issue for any page with three or more open reports, or any
cell with two or more, in the last fortnight (`tools/report_patterns.py`).

The planning notes are in [`planning/`](planning/).
[`planning/CONSOLIDATION_PLAN.md`](planning/CONSOLIDATION_PLAN.md) says how
the materials are being brought together here, in what order, and what has
moved so far. [`planning/PAGE_BY_PAGE.md`](planning/PAGE_BY_PAGE.md) goes
through every page of the three source sites and says what is good, what
should change, and where it belongs.

How the site is made: `build.py` turns the markdown files under
`tutorials/` into web pages in `site/`. A GitHub Actions workflow runs it
on every push to `main` and publishes the result. The front page comes
from `tutorials/front.md`, followed by the list of tutorials. Every
built page has a Settings button and links to the page before it and the
page after it. The workspace page is built by the same script, and is the
one page that loads a code editor (CodeMirror, built from `vendor-src/`
into `assets/vendor/`). [`CLAUDE.md`](CLAUDE.md) says how to run the
build and its checks.

Copies of the two older sites live in [`sources/`](sources/).
`sources/wadb/` is a copy of `WADB_Tutorials`, and `sources/playground/`
is a copy of `HTML-CSS-SQL-JS`. They are not published from here. They
are here so that a rewrite can be checked against the page it replaces.
The originals stay where they are, and the links above point to them.

You can publish your own copy by making a fork of this repository. In
the fork, the Actions tab lets you enable workflows. The publish workflow
then runs on each push to `main`. Its first run turns on GitHub Pages
for the fork.
